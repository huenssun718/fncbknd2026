2.0 更新步驟

1. 先備份 Supabase 的 board_posts、board_keys。
2. 在 Supabase SQL Editor 貼上 migration-v2.0.sql 全文並執行。這是增量更新，請不要重跑原 supabase.sql。
3. SQL 成功後，將 index.html、app.js、table.css 覆蓋上傳 GitHub，保留現有 config.js。
4. 等待 Pages 部署完成，頁尾確認介面版本 2.0。
5. 用自己的管理連結編輯既有單團飯製貼文，確認原選擇保留；測試新貼文兩團與全部團體的篩選。

更新內容
飯製應援的應援團體改為五團複選與「全部團體」。至少選一團；全選會勾五團，取消一團後全選顯示部分選取。福利交換仍維持單一持有團體。
列表與詳情顯示所有選擇的團體；選五團顯示「全部團體」。每篇在各選定團體下都能找到。全部團體只計該篇一次，因此各團篇數相加可能超過總篇數。所有數字依目前區塊、搜尋、場次、狀態、福利及個人檢視條件計算，涵蓋所有分頁。
福利交換表單頂部新增完整注意事項，明確禁止有價轉讓、買賣、補價差交換，以及在公開欄位刊登金額、收付款資訊或補差額需求。這是顯示規範，沒有新增自動文字封鎖或內容審核。

資料庫更新
新增 bands 陣列欄位，舊貼文回填原本 band，保留 legacy band 欄位與資料。更新兩支既有 RPC 以儲存複選團體，保留私人管理金鑰驗證。新增有效團體驗證觸發器與GIN索引。遷移時僅暫停原本已啟用的時間觸發器，避免回填分類改動作者的最後更新時間；整份SQL包在交易內，失敗會回滾。
此檔不會刪除貼文、不更換管理金鑰、不更動公開讀取與管理權限。保留先前1.7時間欄位與觸發器；未執行1.7者仍需依該版說明處理。

驗證
本機已通過：全選/取消/部分選取、至少一團驗證、兩團/五團發布與編輯回填、分團篩選、總篇數不重複、福利交換表單規範、原有發布/管理連結流程。正式Supabase尚未執行本次遷移，SQL及新複選查詢需部署後驗證；未寫入正式資料。
